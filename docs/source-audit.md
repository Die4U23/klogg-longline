# 固定基线源码审计与 M0 复现提案

日期：2026-10-17。基线：`25c7de6d8f6da2ce6a00882e5af70b4f331af4c5`。

检查的快照：`.local/baseline/klogg-25c7de6d8f6da2ce6a00882e5af70b4f331af4c5/`。下文所有源码引用均相对于该快照。本次审计未修改应用代码、未运行应用或测试二进制，也未测量分配、延迟或 GUI 响应性。以下三个发现按严重程度排列，描述的是源码属性和复现提案，不是已完成的 M0 证据，也不表示已复现历史问题 #773/#803。

## 1. 高：压缩块跨度会无条件缩窄到 32 位

`src/logdata/src/compressedlinestorage.cpp:76-90` 会追加完整的 `OffsetInFile`，同时用 `type_safe::narrow_cast<uint32_t>` 存储 `pos - currentLinesBlock_.front()`。达到恰好 128 个端点时压缩该块（`:40`、`:85-86`）。读取压缩块时会用解码出的 32 位值重建偏移（`:127-132`、`:208-219`）。未完成的块会直接返回原始 64 位 vector（`:123-124`、`:200-203`），小规模测试可能因此掩盖问题。`OffsetInFile` 本身是有符号 64 位类型（`src/logdata/include/linetypes.h:46`）。此实现没有显式跨度校验或无损回退表示。

实际行为仍取决于配置的 type_safe 合约策略：受检缩窄可能终止执行；未受检转换则会丢失高位。构建前不要断言具体会发生哪一种。依赖版本为 type_safe 0.2.4（`3rdparty/CMakeLists.txt:8`）。

现有 `tests/unit/linepositionarray_test.cpp:198-239` 覆盖了绝对偏移跨过 UINT32_MAX 的情况，但前三个端点只相差 40 字节。它没有测试块内相对跨度达到或超过 `2^32` 的情况。

最小且有意义的可执行测试应放在现有 `klogg_tests` 目标中，并实际调用生产代码 `LinePositionArray`/`CompressedLinePositionStorage`：

```cpp
LinePositionArray positions;
std::vector<int64_t> expected{1};
positions.append(OffsetInFile(1));
for (int64_t i = 1; i < 128; ++i) {
    expected.push_back((int64_t{1} << 32) + i);
    positions.append(OffsetInFile(expected.back()));
}
for (size_t i = 0; i < expected.size(); ++i)
    REQUIRE(positions.at(i).get() == expected[i]);
const auto range = positions.range(0_lnum, 128_lcount);
for (size_t i = 0; i < expected.size(); ++i)
    REQUIRE(range[i].get() == expected[i]);
```

分别运行以下对照：高绝对起点但相对跨度较小、相对跨度为 UINT32_MAX、相对跨度为 `2^32`，以及 127 与 128 个端点。受检构建中的进程中止应记录为基线失败，不能算作测试基础设施通过。未来修复后，还要覆盖 `pop_back`、替换合成最终 LF、追加和重新压缩路径；这些路径共用索引块元数据。即使该测试只需极少内存，也要记录测试耗时和实际分配/峰值内存证据。不能用重复实现的算术模型代替对真实源码的编译。

真实文件集成提案：将文件精确生成到 5 GiB，内容为 `LF + A*(5*GiB-128) + LF*127`。它有恰好 128 个行端点：一个空首行、一条长行和 126 个空尾行。通过 `LogData::attachFile` 打开，强制使用 UTF-8 并等待 `loadingFinished`。断言共有 128 行，然后只请求 `getLinesRaw(127_lnum, 1_lcount)`：缓冲区必须只有一个 LF。其索引前后端点位于第一个压缩块中。如果它们发生 4 GiB 回绕，该读取会落到长串 A 的内部。这样可验证真实索引器、压缩存储和 QFile 读取，而无需让 GUI 或搜索工作线程物化 5 GiB 的单行。该测试样例必须实际写入并计算哈希，才符合 PRD 对实体文件测试的要求；只调整偏移的稀疏测试样例只能作为补充。只有一条 5 GiB 行的文件无法触发此压缩块跨度问题，因为其唯一相对端点为零。

复现后最小的修复方向：保留现有索引，但为宽跨度块提供明确且无损的表示。普通块继续使用 32 位压缩；固定 128 项的块可保存宽跨度回退数据，或保存更宽的块内增量高位。单纯饱和/拒绝转换、只改变顶层偏移类型，或在不改变 `index / 128` 查找逻辑时拆分可变长度块，都不够。单独修复索引不能证明搜索/预览有界。

## 2. 高：取消路径会遗弃拥有原始指针的对象

`src/logdata/src/logfiltereddataworker.cpp:307` 将图消息定义为 `SearchBlockData*`；`:439` 用 `new` 分配每个块。正常释放只有结果处理器中的 `delete blockData`（`:398`）。同一处理器在中断时会于 `:368-370` 提前返回，因此不会执行 delete。所有走到该分支的已接收消息都会保留其 `RawLines` 缓冲区。如果中断导致 `try_put` 循环失败退出，生产者也不会释放当前指针（`:454-456`）。缓冲区/限流器节点持有的是指针值，而不是指针指向的 C++ 对象。工作线程会等待图完成（`:459`），但没有图级数据载荷清理逻辑。

取消响应性是相关但独立的测量问题：转换和逐行匹配循环没有中断参数/检查（`:99-122`）；匹配器进入该调用前才检查取消（`:327-340`）。因此，单行或整批处理可能在请求取消后继续执行。仅凭这些源码事实无法得出实测取消延迟，也不能证明某个正则表达式会卡住。

专项集成测试应使用真实 `LogData` 与 `LogFilteredData`/工作线程，固定一个匹配线程和每批一行，并索引包含足够多 16 或 64 MiB UTF-8 长行的可重复文件，以占满 限流器。启动受支持的区分大小写字面量搜索，在块活跃时调用 `interruptSearch()`。等待工作线程真正完成，销毁会话，再用完全相同的输入重复。记录取消请求时间、完成时间、存活分配和保留的块字节数。在 `new SearchBlockData` 与其 `RawLines::buffer` 分配处使用 sanitizer/内存泄漏分析器 栈作为决定性证据；进程 RSS 增长单独不足以证明泄漏，因为 内存分配器可能缓存内存。

为提高确定性，可在独立诊断构建中增加分配/销毁计数器，并在结果处理器的中断检查前增加测试屏障；再为生产者 `try_put` 周围增加第二个场景。调用真实取消 API 后释放屏障，并要求未完成数据载荷数量/字节数回到零。保留这些变更作为仅用于诊断的补丁，并将计时结果标为合成结果；测试屏障不能证明基线取消延迟。还要运行未经修改的基线工作负载。不要用复制的 TBB 图小样例替代产品工作线程。

复现后最小修复方向：对可复制的图消息使用共享所有权，或仔细保证每个已接收、拒绝、取消或异常的数据载荷都只有一个清晰所有者和清理路径。现有图拓扑和线程数可以保留。只在一个提前返回分支里补 `delete`，可能仍会漏掉生产者拒绝和异常路径。修复泄漏本身也不会增加行内取消能力。

## 3. 中：搜索和 GUI 防护之前会先读取整行，尚待测量

`src/logdata/src/logdata.cpp:370-389` 根据请求行端点计算总范围，先将 `RawLines::buffer` 调整大小 到整个字节长度，再执行读取。`src/logdata/src/logfiltereddataworker.cpp:302-309` 限制行数和任务数，但 `:432-439` 会在尝试 限流器 准入前读取整批。因此，除了已准入的缓冲区，生产者自身还可能持有一个缓冲区；即便一个 批次 只有一行，也没有按字节限制。

没有预过滤的 UTF-8 路径已经使用原始缓冲区的视图（`src/logdata/src/logdata.cpp:524-525`）：不要将无条件 UTF-8 转码复制归因于这个分支。其他路径会构建 UTF-16 数据，并将 UTF-8 缓存调整至 `buffer.size()*4`（`:529-551`），需要分别观察分配。

GUI 绘制路径调用 `getLines(firstLine_, nbLines)`（`src/ui/src/abstractlogview.cpp:2307`）；自动换行会获取完整展开字符串（`:2151-2152`）。`LogData::doGetLineString` 和展开都会委托完整读取/解码（`src/logdata/src/logdata.cpp:313-321`）。解码器约 1 GiB 的行警告（`:473-476`）发生在 `getLinesRaw` 已分配并读取完整原始行之后（`:418-419`），因此不能阻止该分配。这些源码事实明确了分配边界，但未测量 500 ms GUI 卡顿，也不能证明 macOS 历史问题。

聚焦 M0 工作负载：生成确定性的 LF 结尾 ASCII/UTF-8 文件，包含普通短行对照，以及各含一条 1、16、64 MiB 长行的文件；再单独测试制表符密集的长行。将字面量目标放在靠近末尾处，以验证搜索完整性。通过真实应用/会话：在不渲染长行的情况下加载并搜索它，将其滚动到可见区域，切换自动换行，并另行启动一次搜索后取消。使用 GUI 线程 `QTimer`、单调时钟和分配/CPU 调用栈区分建索引、`getLinesRaw`、转换、匹配以及绘制/`untabify` 工作。捕获原始心跳时间和 工作集/专用字节数（Working Set/Private Bytes）；定位 `RawLines::buffer::resize` 持有的字节，而非只记录总 RSS。离屏后端测试可以显示读取大小/分配情况，但不能证明原生 Windows GUI 响应性。热缓存和缓存状态不受控的结果要如实标注。

最小修复方向取决于实测热点。如果唯一已证明的问题是索引缺陷，应先修索引。如果读取/GUI 路径确实超出冻结的资源/延迟目标，再在分配前引入有界字节范围访问，并让完整搜索独立于预览；降低按行计数的批次 无法限制单条长行。不能仅凭源码审计就实现新匹配器或 GUI 预览框架。
